# AxuTestFramework 分阶段可用性改造方案

> 面向实施 Agent 的任务说明与验收清单。目标读者包括不了解 AxuTestFramework 内部架构的 Unity 开发者。
>
> 状态：待实施。2026-09-23 基于代码静态评审制定；实施前须核对当前代码与运行行为。

## 目标

让首次打开 `AxuFrameKit/AxuTestRunner` 的使用者，无需先读 README、编写 suite JSON 或理解 Agent/Pipeline 术语，就能完成一次测试，知道运行何时结束、结果是否可信、失败后该做什么。

成功体验应是：**打开窗口 → 选择想检查的内容 → 点击运行 → 自动收尾 → 看懂结论与下一步**。

本方案采取定向改造。保留 Core/Agent 分层、既有能力、报告 schema 和可供自动化使用的命令接口；不要为界面改版重写整个测试平台。每阶段单独提交、验证、评审，通过后再做下一阶段。

## 当前观察与待核实问题

1. 总览已有中文结论和“运行场景套件”入口，但首次运行仍要求先从 Assets 中选 `.suite.json` / `.scenario.json`；导出 JUnit、打开 JSON、工件目录等开发者功能与主要运行操作同时呈现。参见 `Editor/Window/AxuTestRunnerWindow.Overview.cs`、`Editor/Window/AxuTestRunnerWindow.ScenarioTrend.cs`。
2. 看板的场景运行按钮调用 `ScenarioRunMenu.TryRunSuite`，该路径进入 Play 后不由 `ScenarioRunService` 的命令看门狗自动退出；看板在退出 Play 后才回读报告。界面文案“跑完自动回显结果”与实际操作不一致。参见 `Editor/Window/AxuTestRunnerWindow.ScenarioTrend.cs`、`Editor/Scenarios/ScenarioRunMenu.cs`、`Editor/Scenarios/ScenarioRunService.cs`。
3. `SuiteDef.Validate` 要求 `ref` 指向同文件内联定义，但 `SuiteLoader.Resolve` 和 `Agent/Capabilities/GameHook/DOC.md` 支持进程内注册的纯 `ref`。文件加载先校验，实际会阻断这一用法。现有 `SuiteLoaderExternalTests` 仅直接调用 `Resolve`。
4. 场景/UTF 运行中的状态按启动时间超过 15 分钟即被视为陈旧。长时间 soak 可仍在运行，此时新命令可能通过互斥检查。参见 `Editor/Scenarios/ScenarioRunService.cs`、`Editor/Commands/AxuTestRunService.cs`。
5. `mode=all` 在 EditMode 失败或超时后仍启动 PlayMode，并覆盖返回状态；整体结论不清楚。参见 `Editor/Commands/AxuTestRunService.cs`。

以上是实施起点，不替代运行验证。修复时保留能复现问题的最小用例和证据。

## 阶段 1：运行闭环与可信状态

**目的：** 用户发起一次运行后，必定能得到本次运行的明确终态，界面不会停在“似乎还在运行”的状态。

实施内容：

- 让看板、菜单和 Pipeline 共享清楚的启动/收尾契约。看板发起的场景运行应在 Agent 写出终态后自动退出 Play、加载本次报告；用户手动停止时显示“已中断”，不能回显旧报告。
- 对成功、测试失败、suite 加载失败、报告写入失败和用户中断分别给出可辨识的终态。状态与报告应有本次运行标识或时间校验，避免陈旧文件被当作本次结果。
- 修复纯 `ref` 代码态 scenario 的文件加载链路：允许已注册定义满足引用，同时保留缺失引用的清楚报错。
- 修复长跑互斥：不能仅依据启动时间判定仍在更新的运行已结束。至少覆盖超过 15 分钟的 soak 与同时发起 UTF 测试的情况。
- 规定 `mode=all` 的双阶段语义，分别保留 EditMode/PlayMode 结果，并给出整体结论；任一阶段失败或超时不得被另一个阶段的状态掩盖。是否继续执行第二阶段可由实现选择，但须写明并测试。

验收：

- 看板发起的场景运行无需用户手动退出 Play，即能看到本次结果。
- 成功、失败、加载错误、手动停止均能到达明确终态；界面不会把上一次报告当作本次报告。
- 运行中的 20 分钟 soak 不允许同一 Editor 启动另一项互斥测试。
- 纯 `ref` 注册 scenario 可由真实 suite 文件加载；未知 `ref` 给出明确错误。
- `mode=all` 的返回值和报告能说明两个阶段各自的结果。

## 阶段 2：首次使用路径

**目的：** 无需任何用户自建 JSON，就能在看板中完成第一次测试。

实施内容：

- 首页设置单一、明显的首次操作，例如“运行示例测试”。使用自包含示例（建议 `echo`），不依赖项目场景或外部服务。示例应区分“测试工具链可用”和“项目功能全部通过”，避免误导。
- 将主要入口按用户目标组织，例如“检查代码功能”“检查场景能否运行”“查看性能变化”。在选择目标后再显示 EditMode/PlayMode、suite、采样等设置。
- 对运行前提做可操作的预检。缺少 `AXU_TEST_AGENT` 或其他必需条件时，说明影响并提供修复入口；不要允许用户进入一个必然不会执行测试的 Play 状态。
- 没有 suite 文件时提供“使用示例”或“创建最小配置”入口，而不是只显示文件扩展名和菜单路径。

验收：

- 对项目不了解的人，打开窗口后无需读文档、编辑文件即可完成一次工具链自检。
- 用户能看出示例测试通过并不等于项目全部测试通过。
- 缺少前提条件时，按钮给出原因及可执行的处理方式。

## 阶段 3：结果解释与信息层级

**目的：** 用户不展开技术详情，也能回答“通过了吗、哪里出问题、下一步做什么”。

实施内容：

- 首屏展示本次运行状态、测试范围、运行时间、通过/警告/失败数量和最需要处理的事项。
- 把 UTF 单元测试与 scenario 场景测试的状态清楚区分。总览若只展示其中一种，应显式标注；“全部通过”必须限定范围。
- 每条失败/警告提供简短中文解释、对应测试或场景、建议检查方向。保留原始错误信息供展开查看，不要用笼统翻译吞掉关键细节。
- 原始指标键、预算/基线明细、堆栈、JSON、JUnit 和工件目录放在“技术详情/导出”区域。常用操作与导出操作在视觉上分层。
- 为“未运行”“正在运行”“已中断”“没有配置预算”“有警告但未失败”定义稳定且互不混淆的呈现。

验收：

- 未参与开发的人只看默认视图，可以说出本次测试的范围、结论和下一步。
- 失败定位所需的原始消息、堆栈、指标仍可在技术详情中找到。
- 总览不会把示例自检或单一种类测试的通过表述为整个项目通过。

## 阶段 4：快速上手与实际使用验证

**目的：** 文档与界面共同服务真实使用任务，而非复述内部架构。

实施内容：

- 增加一页简短快速上手，覆盖三件事：“验证一次代码改动”“检查场景能否正常运行”“比较一次性能变化”。每件事只写前提、点击步骤、预期结果及常见失败处理。
- README 保留完整 API、schema 和命令说明；快速上手从 README 顶部及看板帮助入口可达。
- 请至少一位未参与本系统开发的人照快速上手完成首次运行，记录卡住的步骤和误解，修正界面或文档后再验收。

验收：

- 三个任务都能照文档完成，且步骤与当前 UI 文案一致。
- 首次使用反馈中的每个阻塞点都有处理记录；不以“用户需要理解内部术语”为解决方案。

## 实施边界与验证纪律

- 先修运行正确性，再改交互文案。不要通过改文案掩盖运行不能自动收尾或状态不可靠的问题。
- 保持既有报告 schema、Pipeline 命令兼容；如确需变更，单独说明迁移影响并提供兼容验证。
- 不直接编辑 Unity 场景、Prefab、Asset 的 YAML。涉及 Editor 驱动、编译或测试时，遵循根目录 `AGENTS.md` 指向的 `Packages/com.cielevel.axu-unity-cli-kit/Skills~/unity-cli-workflows/SKILL.md`。
- 不执行无程序集/测试名过滤的裸 `run_tests`；长 PlayMode/soak 运行期间不向同一 Editor 并发派发其他 Pipeline 命令。
- 测试应覆盖真实风险：状态收尾、跨域重载、文件加载、长跑互斥、双阶段结果。避免只验证文案或镜像实现的单测。

## 每阶段交付给评审者的材料

1. 独立提交或清晰的 diff，附变更摘要和设计取舍。
2. 验收项逐条结果；注明实际运行的 Unity 版本、测试命令/过滤范围、通过与失败数量。环境无法运行时如实说明，勿声称已通过。
3. 看板关键状态截图：首次使用、运行中、成功、失败/中断；如某阶段不涉及界面，注明不适用。
4. 已知限制、兼容性影响、仍需手动验证的项目。

评审顺序：先对照本文件的阶段验收项，再检查实现与测试证据，最后让未参与开发的人实际操作一次。任一阶段未达标时，先修该阶段，不提前开展后续界面扩展。
